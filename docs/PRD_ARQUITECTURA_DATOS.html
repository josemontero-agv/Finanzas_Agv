¿En local, Odoo o Supabase?

Hoy, por defecto en local se consulta Odoo para Cobranzas y Tesorería. Supabase solo entra si se activa explícitamente con COLLECTIONS_SOURCE=supabase.

La decisión la toma una sola variable en el backend Flask (get_collections_provider() en app/collections/routes.py):

source = (current_app.config.get('COLLECTIONS_SOURCE') or 'odoo').strip().lower()
if source == 'supabase':
    return CollectionsSupabaseProvider(current_app.config.get('SUPABASE_DB_URI'))
return CollectionsService(odoo_repo)  # Odoo en vivo

Resumen ejecutivo (1 página)

Problema

Cada filtro en Cobranzas golpeaba Odoo en vivo → respuestas lentas, frágiles y con riesgo de sobrecarga al ERP.

Solución

Odoo se consulta una vez cada 15 min vía ETL; los usuarios filtran sobre una copia optimizada en Supabase (PostgreSQL).

Beneficio

Respuestas rápidas, menor riesgo de caída de Odoo, experiencia fluida para el equipo de Créditos/Cobranzas.

Costo infraestructura

~$15/mes

Render Starter (backend + frontend + cron ETL), sin worker Celery ni Redis en producción.

¿Qué ve el usuario en Cobranzas?

Pantalla principal

  • Filtros: fechas, cliente, canal de venta, tipo de documento, sub-canal (Nacional/Internacional), método de pago, número de documento, cuentas contables 12x, fecha de corte histórico.
  • KPIs y resumen: totales de débito, crédito, saldo pendiente, antigüedad de cartera.
  • Tabla de líneas: facturas, notas, letras y movimientos de cuentas por cobrar con estado de pago, vencimiento y saldo residual.
  • Exportación Excel: descarga del reporte filtrado desde el mismo conjunto de datos.

¿De dónde salen los números?

Los números provienen de una copia sincronizada de Odoo almacenada en Supabase — no son consultas en vivo al ERP en cada clic. En producción (cuando se active), la copia se actualiza automáticamente cada ~15 minutos.

Retraso máximo de datos: ~15 minutos respecto a Odoo. Si un pago se registró hace 5 minutos en Odoo, puede no aparecer aún en Cobranzas hasta la próxima sincronización.

¿Qué pasa si los números no cuadran?

  1. El equipo técnico ejecuta el script de paridad (test_collections_parity.py) que compara totales Odoo vs Supabase.
  2. Si hay diferencias (DIFF), se investiga: reset de watermark, re-sync histórico, auditoría de filas discrepantes.
  3. Solo cuando hay 3/3 MATCH en totales (débito, crédito, saldo/residual) se autoriza el go-live con Supabase como fuente.

Excepciones en la interfaz

  • /diagnostics: página técnica que cuenta filas en Supabase directamente (solo diagnóstico, no alimenta el reporte principal).
  • Tesorería: sigue leyendo Odoo en vivo; no usa Supabase aún.

Glosario

ETL (Extract, Transform, Load)
Proceso automático que extrae datos de Odoo, los transforma al formato necesario y los carga en Supabase. Corre cada 15 minutos en producción.
Supabase
Base de datos PostgreSQL en la nube que actúa como "almacén" de la copia de datos de Cobranzas. Permite consultas rápidas sin tocar Odoo.
Fecha de corte (cutoff)
Filtro que limita el reporte a movimientos hasta una fecha específica, útil para análisis histórico de cartera a una fecha determinada.
KPI (Indicador clave)
Métricas resumidas en la parte superior del reporte: totales de débito, crédito, saldo pendiente y distribución por antigüedad.
Paridad
Prueba automatizada que verifica que los totales en Supabase coinciden exactamente con los de Odoo antes de activar la copia en producción.
Watermark (marca de agua)
Registro de la última fecha sincronizada por tipo de dato. Permite que el ETL solo traiga registros nuevos o modificados (sync incremental).

Arquitectura técnica

Finanzas AGV es una aplicación Flask (backend) + Next.js (frontend) desplegada en Render. El piloto Fase 3 desacopla Cobranzas de Odoo en vivo mediante un ETL que puebla tablas en Supabase PostgreSQL.

Componentes clave

  • app/collections/routes.py — endpoints REST de Cobranzas; delega a Odoo o Supabase según COLLECTIONS_SOURCE.
  • app/collections/supabase_provider.py — proveedor alternativo que lee Postgres vía psycopg2 (SQL directo, no PostgREST).
  • scripts/etl/etl_sync_threading.py — ETL Odoo → Supabase con sync incremental por watermark.
  • render.yaml — Blueprint: backend web, frontend Node, cron ETL cada 15 min.
  • config.py — carga de .env según APP_ENV; flags COLLECTIONS_SOURCE, ALLOWED_USERS, etc.

Limitaciones conocidas — supabase_provider.py

1. Cuenta 123 / Letras — trazabilidad factura-origen

La trazabilidad factura-origen para letras (cuenta 123, vía _build_trace_invoice_map en Odoo: bill_form_id → account.bill.form → invoice_ids, con fallback por l10n_latam_boe_number) NO se reproduce en Supabase.

Para cuentas 122/1212/1312/132/13 el resultado es idéntico a Odoo. Para cuenta 123, campos como invoice_origin, invoice_payment_term_id, invoice_user_name, sales_channel_name, linea_comercial muestran valores propios de la letra (pueden venir vacíos).

2. Filtro sub_channel en Python (post-proceso)

El filtro sub_channel no se traduce completamente a SQL. Se aplica en Python después de la consulta (get_report_lines L306-309), lo que puede afectar rendimiento con volúmenes muy grandes.

3. _collapse_1212_lines

Se reutiliza el método estático de CollectionsService importado sin modificar — misma lógica de colapso de líneas 1212 que en Odoo en vivo.

4. Cuenta excluida 1239001

SQL incluye COALESCE(da.code, '') != '1239001' — misma exclusión que el dominio Odoo.

5. Decisión psycopg2 vs PostgREST

Se usa SQL directo parametrizado porque los filtros complejos (prefijos OR, ILIKE, rangos, corte histórico, joins a 6 dimensiones) son más legibles y eficientes que N llamadas HTTP PostgREST.

Requisitos no funcionales

Seguridad

  • SUPABASE_KEY (service role) solo en backend y cron ETL — nunca en frontend.
  • Frontend usa NEXT_PUBLIC_SUPABASE_ANON_KEY (solo lectura limitada por RLS).
  • JWT en cookies HttpOnly (finanzas_agv_access_token, refresh 30 días).
  • OWASP: módulo Letras deshabilitado (LETTERS_MODULE_ENABLED=false) responde 404.
  • Protección CSRF vía chequeo Origin + Content-Type en app/__init__.py.
  • Tabla etl_sync_state con RLS deny-by-default (solo service role).

Control de acceso (lista blanca)

  • Función _is_email_allowed en app/auth/oauth.py: dominio @agrovetmarket.com + presencia en ALLOWED_USERS.
  • Producción: solo 6 usuarios del equipo Créditos/Cobranzas (ver tabla).
  • Desarrollo local puede tener lista más amplia (IT/desarrolladores).
  • ADMIN_EMAILS es opcional y separado; define rol admin en JWT, no sustituye la whitelist.

Disponibilidad

  • ETL como Render Cron Job cada 15 min (*/15 * * * *) — sin worker Celery persistente.
  • Fallback operativo: cambiar COLLECTIONS_SOURCE=odoo en Render sin redeploy de código.
  • Health check backend: /api/health.

Rendimiento

  • Flask lee Postgres vía pooler Supabase (:6543) — conexiones eficientes.
  • Odoo solo se consulta en sync batch (ETL), no en cada request de usuario.
  • Caché Flask 300s en endpoints de reporte (@cache.cached).

Consistencia

  • Paridad automatizada (test_collections_parity.py) con exit code 1 si hay DIFF.
  • Watermark incremental en etl_sync_state — sync solo registros con write_date posterior.
  • Prefijos de cuenta sincronizados entre ETL y servicio Odoo.

Observabilidad

  • /diagnostics — conteo de filas Supabase desde frontend.
  • Logs ETL en stdout (Render cron logs).
  • Script de paridad con salida tabular y exit code para CI/manual.
  • Uso de app (v1): tabla user_activity_logs, API /api/v1/analytics y tablero /observability solo admin (logins, page views, horarios, top usuarios/módulos). Ver skill finanzas-observabilidad.
